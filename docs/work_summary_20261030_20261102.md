## 2. 执行摘要

这几天的核心变化，是把原来“模型在普通正文中输出工具 JSON 或最终答卷”的模糊协议，逐步改造成“原生 provider 工具调用 + 类型化状态机 + 动态封闭工具面 + 独立最终答卷”的执行协议。

主要发现可以分为四层：

1. **模型生成层**：出现过空正文、思考循环、提前 EOS、`tool_request:null`、`final_answer` 错误包装、query/cursor 混配、多工具调用和缺失 call ID。推荐采样减少了早期循环和空正文，但没有消除所有协议错误。
2. **客户端协议层**：发现 null 与缺失字段共用 `None` 哨兵、分页元数据在渲染时丢失、格式修复缺少任务上下文、预算归零后仍暴露工具、A0 条件仍向模型暴露工具 schema 等实现问题。

4. **检索行为层**：正确证据有时首屏已经返回，模型仍继续翻页、重复搜索和重复打开，造成上下文膨胀、预算耗尽与最终答卷空间不足。

### 3.1 2026-10-30：INT4 + MTP 扩展批次启动后暂停

目标是用 20 个此前未调优案例构造 32 个完整任务，检查 INT4 + MTP 在新合同上的稳定性。配置为默认 `30000/v1`、xhigh、`max_tokens=32768`、`timeout=360`、`temperature=0`、单任务串行。

实际运行到 14 个终态任务后暂停：12 个完成、2 个协议失败。暂停时不能据此计算整批准确率；当时的 11 个“暂定正确”也不能替代完整批次统计。主要失败为：

- CASE-0032：Manager 在思考循环后没有可用正文，格式修复又生成空 `target_clause_status`。
- CASE-0078：Compliance 输出 `{"tool_request": null}`；格式修复不携带完整任务上下文，无法还原原判断。

同时记录了两类基础设施问题：监控器曾误读 Unicode record separator，导致一个部分任务中断；恢复包装器与子进程状态不一致，后来通过进程核验接管继续。首次缺少 `--live-batch` 的启动在发出任何模型请求前即被拒绝，不计入实验分母。

处理原则是先 `SIGSTOP` runner/monitor，保留在途状态、原始日志和哈希，不直接把失败任务重跑成成功。

### 3.2 2026-10-30 至 10-31：失败隔离矩阵与第一轮客户端修复

为区分量化、MTP、缓存和 JSON 约束的影响，先后尝试了：

- INT4 + MTP、INT4 无 MTP、BF16 无 MTP；
- 原 JSON 约束、去掉 JSON 约束、重新启用约束；
- 冷缓存、前缀预热、禁用跨请求 radix cache；
- 冻结失败轮的单轮重放与已知案例的完整任务复跑。

得到的结论不是“某一个变量就是根因”，而是：

- CASE-0032 的初次 INT4 + MTP 重放为 1 次合法工具请求、2 次非法输出，不是此前误述的 3/3 失败；该口径已更正。
- 同一约束在重新启动的缓存实例上可以 3/3 通过，因此通用 JSON 约束不是已证明的单一根因。
- 冷缓存和预热缓存会生成不同输出，但都能 3/3 通过，说明存在状态依赖，仍不能定位原始空正文的引擎根因。
- 禁用 radix cache 是隔离措施，不是上游 kernel 修复，也不能保证未见任务稳定。

这一阶段确认了一个真实客户端缺陷：缺少 `tool_request` 键和显式 `tool_request:null` 都被压成同一个 `None` 哨兵。修复后改为区分“字段缺失”和“显式非法 null”，并保留非法请求，不把它静默解释成最终答卷。相关修复经过 117 项检查和 3 次历史上下文实机续写验证。

已知案例的一个六任务复跑得到 6/6 完成且最终动作正确，但仍记录了 3 次 null 工具错误；这只能说明 runner 能在这些运行中恢复并交付，不能说明协议已经干净。

### 3.3 2026-10-31：生成层、EOS 与原始 token 诊断

随后开始保存 SGLang SSE 中的原生 input/output token IDs，并对 BF16/INT4、MTP、缓存、JSON/EBNF、前导空白等条件做冻结单轮诊断。

确认的事实包括：

- 保存的原生输出 token 与服务端 usage 对齐，空正文和 `tool_request:null` 不是客户端凭空拼出来的。
- 某些历史空正文发生在模型先生成 EOS、且引擎在 `</think>` 前接受 EOS 的路径；没有证据表明 parser 吞掉了一段已经生成的正式答案。
- 当前镜像源码没有参考提交 `1c59953` 中“思考未结束时保护 EOS”的逻辑。候选方法只做了 7 项 CPU 方法级检查，没有集成到完整引擎，也没有上线。
- `finish_reason=stop` 本身不能区分正常完成、模型 EOS、用户 stop token 或解析边界，必须结合 `matched_stop` 和原始 token。

同时审计了采样：模型默认是 `temperature=1.0/top_p=.95/top_k=20`，但客户端显式 `temperature=0` 覆盖了默认值，使实际行为变成贪心；只改服务器 preferred sampling 不能改变客户端覆盖。

这一阶段没有全局启用 `ignore_eos`，没有修改运行镜像，也没有把所有历史失败归因于 INT4、MTP、xhigh 或贪心中的任何单一因素。

### 3.5 2026-10-31：分页渲染、修复上下文与前导空白问题

在后续双卡运行的只读审计中，发现三个独立客户端问题：

1. `search_contract` 后端生成了真实 `next_cursor`，但 `render_tool_result` 没把分页元数据放进模型可见文本，模型只好猜出字符串 `"next"`。
2. 重复页在去重后会被渲染成“没有匹配段落”，同时丢掉 `repeat_page` 提示，误导模型判断检索失败。
3. 格式修复请求只包含旧响应和 validation error，不包含 case、目标类别、policy 或证据 ID；它能做格式修正，但无法对完全空输出恢复实质判断。这是既有设计边界，不应把失败归咎于“修复模型不够聪明”。

处理方法：

- 分页结果改为保留完整 JSON 元数据，真实 cursor、query、target category、页码和 repeat notice 都进入模型可见结果。
- 仍保留后端 cursor 绑定校验，绝不在客户端静默替换模型的 query。
- 对旧冻结 null 输入测试“允许正文前导空白”的最小语法。某个冻结输入由 `tool_request:null` 变成完整答卷，说明旧 EBNF 的正文起始限制确实影响了特定路径。

但两条完整任务验证只有 1/2 干净完成：另一条仍出现空正文和失败的格式修复。因此“允许前导空白”只解决了一个具体约束问题，没有解决全部生成失败。

### 3.8 2026-10-31：五条新异常的离线审计与文本协议修复

离线审计显示三条 null 不是旧的前导空白问题：模型分别生成了：

- `{"tool_request": null}`；
- `{"tool_request": null, "final_answer": true}`；
- `{"tool_request": null, "final_answer": {完整答卷}}`。

通用 JSON 语法接受这些对象，但业务协议不接受。显式 null 已被新哨兵逻辑正确拒绝，工具没有真正执行；包含完整嵌套答卷的响应也不能被静默解包，否则会改写实验协议。

两条分页错误则是模型把新 query 与旧 cursor 组合。冻结输入中真实 cursor 和原 query 都完整可见，所以这不再是客户端丢分页元数据，而是模型违反参数关联。

第一版工程修复仍在文本 JSON 层：

- 用严格联合 EBNF 约束“一个合法工具请求或角色正式答卷”，拒绝 null、错误 wrapper 和额外根字段；
- 从当前轮已见分页结果动态构造 cursor → `(query, target_category)` 关系；
- 首次搜索不允许带 cursor，翻页只能使用当前有效绑定。

验证结果为：52 项回归通过；五条冻结错误全部被拒绝；五个冻结输入重新生成 5/5 通过；两个完整任务 2/2 完成，36 次模型请求、32 个工具轮、4 个答卷轮，null/分页/其他工具错误均为 0。这个结果证明已知非法表达被阻断，但不证明模型内部错误倾向消失。

### 3.9 2026-10-31：根因筛查、确定性推理与 null 概率边界

先做了 2×2 单轮筛查：原提示/明确协议提示 × 通用 JSON/无约束，共 20 次。结果为 4/5、5/5、5/5、5/5；历史 null 没有稳定复现。

关键方法学发现是：当前 SGLang 实例的 `enable_deterministic_inference=false`。在这一模式下，MTP verify 不使用请求 seed 构造 `sampling_seed`，而走 `torch.rand` 路径。因此过去“请求 seed 相同”不能被解释为相同随机过程。记录的 seed 仍是真实配置字段，但不能支撑严格配对因果结论。

随后启动确定性隔离实例：

- 两次门槛请求原生输入/输出逐 token 一致；
- 20 次主诊断均正常结束；五组原提示重复 5/5 逐 token 一致；
- 原提示、明确协议、等长中性文字、原提示重复四组都没有复现历史五条异常。

由于原提示本身没有出错，这一轮没有形成“错误 → 修复”的配对样本，也不能把成功归因于提示、去掉 JSON 语法或确定性后端。

最后对三条历史 null 做 teacher-forced 条件评分。固定历史前缀下：

- 在正文第一个字段处，错误的 `tool` 分支仍有约 10.67%–18.24% 的采样概率；
- 一旦走到 `tool_request`，`null` 的条件概率约 43.13%–84.09%，经过 top-k/top-p 后约 43.78%–85.20%；
- 原通用 JSON 语法在这些关键分岔处没有实质改变概率；它只可能在错误对象已经完成后强制结束合法 JSON。

这支持“模型分布本身保留错误格式分支，普通随机采样可选中它”，但不能证明训练来源、提示哪一句或历史引擎状态是唯一根因。

### 3.12 2026-11-01：七层配置、部署闭环和仓库整理

### 3.13 2026-11-01：三卡复制、并发 4 与工程冒烟

先把 GPU2 的 BF16 + MTP 原生服务复制到 GPU0/GPU1。初次复制时 GPU0/1 仍是 300 W，随后三卡统一到 200 W，并把 `max_running_requests` 从 1 提升到 4。

随后对两个历史协议问题做完整串行重跑：

### 3.14 2026-11-01：上下文安全、检索压缩和 bounded-v3

长工具链随后暴露了三个新问题。

**上下文预算溢出。** CASE-0077 的第 16 次 Manager HTTP 输入为 16,477 tokens，旧配置仍声明 32,768 输出，合计 49,245，超过 49,152 上下文 93 tokens。修复为：

- 基础输出上限 16,384；工具轮 8,192（后续 v3 提高到 16,384）；最终 16,384；修复 4,096；
- 每次发送前用冻结 Qwen tokenizer 估算 provider 可见输入；
- 在 49,152 中预留 1,024 安全余量，动态下调 `max_tokens`；
- 若可用输出少于 2,048，记录 `context_budget_failure` 并在本地停止，不发送必然失败的 HTTP。

**检索历史膨胀。** 新增 `retrieval-ledger-v1`：原始工具和审计日志保持 append-only；模型上下文可以原子压缩旧的 assistant/tool 对，替换为带调用序号、query、target、候选 ID 和错误状态的短账本。完整打开的段落永不压缩。输入超过 18,000 时压到约 12,000；连续 3 次检索没有新增段落 ID 后停止暴露搜索/翻页工具。

**无效深翻页和重复打开。** CASE-0077 的正确证据首屏排名第 3，工具序号 6 已完整打开，但模型仍把第三个 query 翻到第 5 页，并再次打开同一段落。`bounded-v3` 因此：

- 每个独立 query 最多 2 页、每页 5 条；
- 规范化重复 query 和重复打开在工具层拒绝并保留日志；
- 拒绝仍消耗共享工具预算；
- 分页上限只定义成本边界，不声称第 2 页后一定没有相关证据。

这些改动都保留旧配置和旧运行，不用新规则重解释历史结果。

## 7. 尚未解决或不能过度解释的事项

1. **96 轮还没有在本文中做研究效应或语义准确率分析。** 96/96 是有效交付覆盖，不是 96/96 判断正确，也不是 V/D 因果效应结论。
2. **原始模型/引擎错误倾向没有全部根治。** closed-v4 阻断非法表达，不能证明模型以后不会产生别的失败模式。
3. **五次恢复成功样本有限。** 它能说明这些身份在该 profile 下完成，不能估计总体故障率为零。
4. **未提交工作树还没有新的全量绿色证明。** 阶段一有 1205 passed；v4 有本地 92 和服务器 283 项专项通过。Windows 广泛套件仍受缺失冻结材料、历史 Gate 产物和网络导入边界测试影响。
5. **文档存在一处已知漂移。** 当前 `docs/experiment_console.md` 仍写本地操作台默认 `retrieval_bounded_v3`，而代码的 local-GPU 默认已是 `experiment_native_tools_closed_v4.yaml`。
6. **缺失 call ID 等分支主要由离线/专项测试覆盖。** 应继续用可控故障注入验证，而不是等待随机实机再次发生。
7. **性能 sweep 尚未完整执行。** 已完成 200 W 工程冒烟和并发验证，但 230/240/250/260 W 三重复、并发 2/4/8/16、FP8 兼容性探针仍主要停留在计划和 harness 阶段。
8. **FP8 不能预设会加速。** A800 是 Ampere，没有 Hopper 原生 FP8 Tensor Core；任何结果都必须记录实际 backend，区分权重 FP8、KV FP8 和端到端 FP8，并防止把静默回退称为加速。
