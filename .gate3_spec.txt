============================================================
GATE 3 — EXPERIMENT EXECUTION + AUTOMATIC SCORING
============================================================

Goal:

Turn the existing single-case workflow into a reproducible experimental engine
that can:

1. execute many case × condition × repeat jobs,
2. assign stable run identities,
3. randomize/interleave execution order reproducibly,
4. preserve all raw execution artifacts,
5. automatically derive experiment outcomes from raw state/logs,
6. export one tidy row per run,
7. reconstruct all processed results from raw artifacts.

DO NOT build the real 12 development cases yet.

5. IMPLEMENT GOLD-BASED AUTOMATIC SCORING
------------------------------------------------------------

Implement scoring as a pure post-processing layer.

CRITICAL RULE:

SCORING MUST NEVER AFFECT THE WORKFLOW.

No scoring function may be imported into:
- prompts
- nodes
- tools
- tool loop
- retrieval
- workflow routing

Gold is read only AFTER or OUTSIDE model execution.

Use deterministic rule-based scoring.

No LLM-as-judge for primary metrics.

Implement at minimum:

--------------------------------------------------
5A. final_action_correct
--------------------------------------------------

Definition:

    compliance final decision == case.gold_action

Return:
- True / False
- None if the run never produced a final Compliance output

Do not reinterpret or "fix" the model answer.

--------------------------------------------------
5B. error_survival_manager
--------------------------------------------------

This metric applies primarily to E1 omission cases.

Interpretation:

Did the omitted upstream target fact remain uncorrected at Manager?

Use the frozen case gold target clause status.

For an E1 case whose target clause is truly present:

    Manager clause_status != present
        → error survived Manager

    Manager clause_status == present
        → Manager corrected the omission

Do NOT infer correction merely because Manager chose ESCALATE.

Decision correctness and fact correction are different.

Return an explicit not-applicable value for cases where the metric is not
conceptually defined.

--------------------------------------------------
5C. error_survival_compliance
--------------------------------------------------

Same principle at Compliance.

For an E1 positive target case:

    Compliance clause_status != present
        → omission survived Compliance

    Compliance clause_status == present
        → omission corrected by Compliance

Do not substitute final action for factual correction.

--------------------------------------------------
5D. correction_stage
--------------------------------------------------

For E1 target-positive cases classify:

- manager
- compliance
- never

Optionally:
- already_correct / not_applicable for E0

Definition must be deterministic from structured outputs.

--------------------------------------------------
5E. corrected_with_evidence
--------------------------------------------------

This is stricter than "correct clause_status".

It is True only if all required components hold:

1. target clause was correctly recovered;
2. node cited evidence;
3. cited evidence was SELF_OPENED by that node;
4. evidence belongs to current contract;
5. cited/opened evidence overlaps or corresponds to the frozen gold evidence
   for the target clause.

IMPORTANT:

Use hidden gold offsets / source mapping ONLY in scoring.

Never expose them to retrieval.

If the current paragraphization means a gold span sits inside a paragraph,
score evidence correctness by deterministic offset overlap between:

    opened paragraph [start_char, end_char)
and
    gold evidence [gold_start, gold_end)

Do NOT require exact string identity if paragraph-level evidence is the
designed retrieval unit.

Preserve enough diagnostics to explain why the metric is false:

- target_not_recovered
- no_evidence
- not_self_opened
- foreign_evidence
- no_gold_overlap

Use enums if appropriate.

--------------------------------------------------
5F. false_escalation
--------------------------------------------------

For negative sentinel cases where gold_action == ACCEPT:

    final decision == ESCALATE
        → false_escalation = True

Otherwise False.

Return not-applicable for positive cases if that makes the processed schema
clearer.

6. SEPARATE FACT, ACTION, AND EVIDENCE
------------------------------------------------------------

The scoring schema must NOT collapse these into a single "correct" field.

At minimum preserve separate columns:

- manager_clause_status_correct
- compliance_clause_status_correct
- final_action_correct
- manager_corrected_with_evidence
- compliance_corrected_with_evidence
- false_escalation

This distinction is scientifically important.

Examples:

Case A:
Manager says UNKNOWN,
Compliance says UNKNOWN,
final_action = ESCALATE

If ESCALATE happens to match gold:
- final_action_correct = True
- target fact was NOT recovered
- corrected_with_evidence = False

That run must NOT be described as successful correction.

Case B:
Manager correctly finds target clause with source evidence,
Compliance inherits it but never independently opens source.

Then:
- Manager self-verification may be evidence-backed
- Compliance may rely on upstream evidence
- Compliance independent corrected_with_evidence must distinguish that from
  self-opened verification

Preserve Gate 2.5's:
SELF_OPENED vs OBSERVED vs UPSTREAM_CITED distinction.
